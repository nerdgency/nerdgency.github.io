# `{exp:formidable:form}`

Renders a form built in the control panel: the `<form>` element, its hidden processing inputs, its pages, sections and fields, their values and errors, and the navigation. With no markup between the tags it renders everything from the form's [theme](/docs/formidable/displaying-forms/themes). Any part can be replaced with your own markup. See [Render a form your way](/docs/formidable/displaying-forms/rendering).


```ee title="templates/default_site/contact.group/index.html"
{exp:formidable:form form_handle="contact_us"}
```

The tag can be used as a single tag, as above, or as a pair with markup between the tags.

## Parameters

Every parameter name on this page is checked against the add-on's source when the documentation builds.

### Choosing the form

<Param tag="form" name="form_handle" required="One of these" example='form_handle="contact_us"'>

The handle of the form to render. Handles are the same across environments, so prefer them to ids.

</Param>

<Param tag="form" name="form_id" required="One of these" example='form_id="3"'>

The id of the form to render.

</Param>

If neither is given or neither matches, the tag renders its `{if no_results}` block, or halts with a message under `debug="on"`.

<Param tag="form" name="debug" default="off" values={<><code>on</code>, <code>yes</code>, <code>y</code>, <code>true</code>, <code>1</code></>}>

Turns quiet fallbacks into errors that name the problem: a missing form, a form with no fields, or fields filtered out. Use it while building, and turn it off on a live site. See [Troubleshooting](/docs/formidable/getting-started/troubleshooting).

</Param>

### After submitting

<Param tag="form" name="return" default="the page the form was submitted from" example='return="contact/thanks/SUBMISSION_HANDLE"'>

Where to send the visitor after a successful submission: a template path or a full URL. Two tokens are replaced if present:

| Token | Replaced with |
| --- | --- |
| `SUBMISSION_HANDLE` | The new submission's random public handle |
| `SUBMISSION_ID` | Its sequential id |

Prefer `SUBMISSION_HANDLE`. A sequential id lets a visitor guess their neighbours' ids. When the form does not store submissions there is nothing to reference, and the tokens are left as they are.

A URL on another host is refused unless that host is listed in `$config['formidable_return_hosts']`. Inherits from the form's and the site's **Return** setting. See [Settings and inheritance](/docs/formidable/building-forms/settings).

</Param>

<Param tag="form" name="return_on_error" default="the page the form was submitted from" example='return_on_error="contact"'>

Where to send the visitor when validation fails. The form there shows its errors and keeps what was typed. The submitting page is recorded in the signed form meta as the form renders, so this works even when the browser sends no `Referer` header. On a URL with segments, the recorded address leaves out the query string. Set `return_on_error=` explicitly if you need one.

</Param>

<Param tag="form" name="success_message" default="the form's, then the site's" example='success_message="Thanks, we will be in touch."'>

The message `{form_success_notice}` and `{form_success_message}` show after a successful submission.

</Param>

<Param tag="form" name="success_values" default="no" values={<><code>yes</code>, <code>no</code></>}>

Makes the submitted answers available after a successful submission as `{submission:HANDLE}`. It is off by default, because it writes the visitor's answers into the session's flash data on a path that does not otherwise need them.

</Param>

<Param tag="form" name="submission_handle" example='submission_handle="{segment_3}"'>

Pre-fills every field from a stored submission, identified by its public handle, never by its id. Submitting the form then **updates that submission** instead of creating a new one, and raises the **Submission Updated** workflow event. A handle belonging to another form is ignored, and so is an unknown one. Encrypted answers are decrypted to fill the form.

:::warning A handle is not a password
The handle is unguessable, but anyone holding it can see and change that submission's answers on a page that uses it. Restrict the template, for example to the member who made the submission. See [Edit a submission](/docs/formidable/submissions/front-end-editing).
:::

</Param>

### Access

<Param tag="form" name="members_only" default="the form's, then the site's" values={<><code>yes</code>, <code>no</code></>}>

Only logged-in members may fill the form in. A guest sees the members-only message instead of the form, and a guest's submission is refused however it arrives. To place the message in your own markup, use the [closed-form variables](#closed-forms), whose reason is `members`.

</Param>

<Param tag="form" name="members_only_message" example='members_only_message="Please log in to apply."'>

The message guests see on a members-only form.

</Param>

<Param tag="form" name="drafts" default="the form's, then the site's (off)" values={<><code>yes</code>, <code>no</code></>}>

Save and resume: a **Save and continue later** button on each page, and a resumed draft filled in from its link or for its member. See [Save and resume](/docs/formidable/submissions/save-and-resume).

</Param>

<Param tag="form" name="draft_save_label" example='draft_save_label="Finish later"'>

The Save button's text.

</Param>

<Param tag="form" name="draft_autosave" default="the form's, then the site's (off)" values={<><code>yes</code>, <code>no</code></>}>

With `drafts` on, also save the draft quietly each time the visitor presses Next.

</Param>

### Which fields render

<Param tag="form" name="only" example='only="first_name|email_address"'>

Pipe-separated field handles. The `{fields}` loop renders only these.

</Param>

<Param tag="form" name="exclude" example='exclude="email_address"'>

Pipe-separated field handles. The `{fields}` loop renders everything except these. If both are given, `only=` wins. Use `exclude=` when you place a few fields by hand with [named fields](#named-fields) and let the loop render the rest.

</Param>

:::note Left out is not removed
A field left out of the loop is still part of the form, and its rules still apply on submission. A required field you leave out fails validation with nothing on the page to correct. Relax it with `field:HANDLE:rules=`. Invisible fields, such as Hidden, CAPTCHA and Turnstile, render inside `{form_meta}` and are not affected by `only=` or `exclude=`.
:::

<Param tag="form" name="page" example='page="2"'>

Renders only that page of a multi-page form, as its own submission. The page's navigation becomes a single submit button. Without it, every page renders and the visitor steps through them in the browser. See [Multi-page forms](/docs/formidable/building-forms/multi-page-forms).

</Param>

### Appearance

<Param tag="form" name="theme" default="the form's, then the site's, then default" example='theme="bootstrap"'>

The [theme](/docs/formidable/displaying-forms/themes) for this render: `default`, `tailwind`, `bootstrap`, or a template group a theme was copied into.

</Param>

<Param tag="form" name="template_columns" default="the form's, then the site's, then 12" example='template_columns="16"'>

The width of your site's grid. Each field's width in the builder (a quarter, half, three-quarters or all of the row) is scaled to it and published as `{field_columns}`, so `col-span-{field_columns}` works with any grid.

</Param>

<Param tag="form" name="page_heading_level" default="each page's own level (2 unless changed)" example='page_heading_level="3"'>

The heading level for page names, `1` to `6`, published as `{page_heading_tag}`.

</Param>

<Param tag="form" name="section_heading_level" default="each section's own level (3 unless changed)" example='section_heading_level="4"'>

The heading level for section names, `1` to `6`, published as `{section_heading_tag}`.

</Param>

<Param tag="form" name="error_heading" example='error_heading="Please check these answers"'>

The heading of the error summary.

</Param>

<Param tag="form" name="prefix" example='prefix="signup_"'>

Prefixes every variable the tag publishes, so two forms on one page do not collide. With `prefix="signup_"`, `{form_attributes}` becomes `{signup_form_attributes}`. Theme parts are written without prefixes and work whatever prefix the tag uses.

</Param>

### Structure switches

Placing a composite variable yourself already stops Formidable adding its own, so these are rarely needed.

<Param tag="form" name="include_form_wrapper" default="detected" values={<><code>yes</code>, <code>no</code></>}>

Whether the tag writes the `<form>` element. A literal `<form` in your markup is detected, and the tag writes none. Use `no` when the `<form>` is **outside** the tag, in your page, where the tag cannot see it. Use `yes` to force the wrapper.

</Param>

<Param tag="form" name="include_meta_wrapper" default="yes" values={<><code>yes</code>, <code>no</code></>}>

Whether `{form_meta}`'s hidden inputs are wrapped in their own hidden `<div>`.

</Param>

<Param tag="form" name="include_content_wrapper" default="yes" values={<><code>yes</code>, <code>no</code></>}>

Whether `{form_fields}` has its wrapping `<div>`.

</Param>

<Param tag="form" name="include_error_summary" default="yes" values={<><code>yes</code>, <code>no</code></>}>

Whether the error summary renders at all, including `{form_error_summary}`. Each field still shows its own error.

</Param>

<Param tag="form" name="include_success_notice" default="yes" values={<><code>yes</code>, <code>no</code></>}>

Whether the success notice renders at all, including `{form_success_notice}`.

</Param>

<Param tag="form" name="include_page_progress" default="yes" values={<><code>yes</code>, <code>no</code></>}>

Whether the step indicator renders on a multi-page form. The page navigation is not affected.

</Param>

<Param tag="form" name="include_js" default="yes" values={<><code>yes</code>, <code>no</code></>}>

Whether `formidable.js` is added to the page when the form needs it: for conditions, multiple pages, Computed fields, the JavaScript honeypot, or disabling the submit button while sending. Scripts a fieldtype needs, such as the signature pad, are always added.

</Param>

### Spam

<Param tag="form" name="honeypot" default="formidable_hp" example='honeypot="your_website"'>

The name of the honeypot input, when the form's honeypot is on.

</Param>

<Param tag="form" name="honeypot_js" default="_formidable_js_ok" example='honeypot_js="_ok"'>

The name of the JavaScript honeypot input, when that honeypot is on.

</Param>

### Output

<Param tag="form" name="output" values={<code>json</code>}>

`output="json"` returns the form as a JSON document instead of markup, for a template of type JSON or a script that renders the form itself. See [Form JSON](/docs/formidable/headless/form-json).

</Param>

### Attributes, settings and rules for one render

<Param tag="form" name="REGION:attribute:NAME" example='label:attribute:class="form-label"'>

Sets one attribute on every instance of a region. `class` appends to what other layers set. Start the value with `=` to replace. Any region works. See [Regions and attributes](/docs/formidable/displaying-forms/regions-and-attributes) for the list. The `<form>` element is the `form` region: `form:attribute:novalidate=""`.

</Param>

<Param tag="form" name="field:HANDLE:REGION:attribute:NAME" example='field:email_address:label:attribute:class="sr-only"'>

The same, for one field. Only field-level and option-level regions take this form: <RegionList level="field" />.

</Param>

<Param tag="form" name="field:HANDLE:attribute:NAME" example='field:email_address:attribute:placeholder="you@example.com"'>

One attribute on one field's input. Short for `field:HANDLE:field:attribute:NAME`.

</Param>

<Param tag="form" name="form:setting:NAME" example='form:setting:enable_storage="no"'>

Overrides one of the form's settings for this render, without changing the saved form. Accepted names: <FormSettingsList />. Booleans accept `yes`/`no`, `1`/`0`, `true`/`false` and `on`/`off`. Unknown names are ignored. Settings that affect what is stored travel to the server in the signed form meta, so they apply to the submission too.

</Param>

<Param tag="form" name="field:HANDLE:rules" example='field:email_address:rules="required|email"'>

Adds validation rules to one field for this render and its submission, in ExpressionEngine's rule syntax. Rules merge with the field's saved rules by name. Start the value with `=` to replace them:

```text
field:email_address:rules="email"     adds to the saved rules
field:email_address:rules="=email"    replaces them
field:email_address:rules="="         removes them
```

A pipe inside brackets belongs to the rule: `enum[editor|author|guest]` is one rule. The rules travel to the server in the signed form meta, so they change real validation. See [Validation rules](/docs/formidable/building-forms/validation#rules).

</Param>

## Composite variables

Each composite renders one structural part. **Placing one is what tells the tag not to add its own.** Write the expansion instead when you want the markup to be yours.

| Variable | Renders |
| --- | --- |
| `{form_meta}` | The hidden block: signed meta, CSRF token, honeypots, and any invisible fields. Every form must place it. If you forget, it is added after your `<form>` tag. |
| `{form_success_notice}` | The success notice, once, after a successful submission. Nothing otherwise. |
| `{form_error_summary}` | The error summary after a failed submission. Nothing otherwise. |
| `{form_page_progress}` | The step indicator on a multi-page form. |
| `{form_fields}` | The content wrapper with every page, section and field in it. |

With no markup between the tags, the theme's `_form` part renders, which for every shipped theme is:

```ee title="The Default theme's _form part (comment removed)"
{form_meta}

{form_success_notice}

{form_error_summary}

{form_page_progress}

{form_fields}
```

…inside a generated `<form {form_attributes}>`.

## Form variables

| Variable | |
| --- | --- |
| `{form_id}`, `{form_handle}`, `{form_name}` | The form |
| `{form_attributes}` | Every `<form>` attribute: `id`, `name`, `method`, `action`, `enctype` when the form has a file field, and anything set on the form or the tag. Takes the `:bag` modifier. |
| `{form_attribute:NAME}` | One attribute's value, such as `{form_attribute:action}` |
| `{form_page}`, `{form_page_count}` | The current page number and the number of pages |
| `{form_is_captured}` | Whether the form was made by `{exp:formidable:capture}` |
| `{form_stores_submissions}`, `{form_stores_submission_data}` | Whether submissions, and their answers, are stored |
| `{form_shows_instructions}` | `t` or `b`, where instructions go. Also `{form_shows_instructions_on_top}` and `{form_shows_instructions_on_bottom}`. |
| `{statuses}…{/statuses}` | The form's statuses, with `{status_id}`, `{status_name}`, `{status_handle}` and `{status_color}` |

## Fields

### The `{fields}` loop

Loops over every field that renders in the layout, in builder order (page, then section, then position), limited by `page=`, `only=` and `exclude=`. Inside it:

| Variable | |
| --- | --- |
| `{field_template}` | The field rendered in full by the theme: its `_field` shell around its `_control` |
| `{field_id}`, `{field_handle}`, `{field_name}` | The field's id, handle (also its default `id` and `name`), and label text |
| `{field_type}`, `{field_group}` | The fieldtype's handle (`email`) and its group's (`inputs`) |
| `{field_label}` | A complete `<label>` bound to the input |
| `{field_instructions}` | The instructions as plain text |
| `{field_instructions_top}`, `{field_instructions_bottom}` | The instructions element, filled only in the position the form uses |
| `{field_attributes}` | Every attribute for the input. Takes `:bag`. |
| `{field_attribute:NAME}` | One input attribute's value |
| `{field_wrapper_attributes}` | Attributes for the field's outer element, including `data-formidable-*` hooks for columns, pages and conditions. Takes `:bag`. |
| `{field_wrapper_attribute:NAME}` | One wrapper attribute's value |
| `{label_attributes}`, `{instructions_attributes}`, `{error_attributes}`, `{options_wrapper_attributes}` | The other field-level regions |
| `{field_value}` | The value to show: what was submitted, else the stored submission's, else the default |
| `{field_submitted_value}` | Only what this visitor sent, so "left blank" can be told from "not asked yet" |
| `{field_content}` | The content of an HTML field, and the markup of special fieldtypes |
| `{field_required_mark}` | `<span class="formidable-required-mark" aria-hidden="true">*</span>` when the field is required, else nothing. `{field_label}` already ends with it |
| `{field_files}…{/field_files}` | A File field's stored files when `submission_handle=` (or a resumed draft) fills the form: `{file_id}`, `{file_name}`, `{file_url}`, `{file_is_image}`. With `{field_files_count}`, `{field_files_note}` (what the boxes do), and `{field_files_keep}`, the name for each file's keep box (`value="{file_id}"`, after one empty hidden input of the same name) |
| `{field_columns}` | The field's width in your grid. See `template_columns=`. |
| `{field_page}`, `{field_section}` | The page number and section id the field is in |
| `{field_error}`, `{field_has_error}` | The validation message, and whether there is one |
| `{field_is_required}`, `{field_is_hidden}` | Conditionals |
| `{field_has_conditions_show}`, `{field_conditions_show}`, `{field_conditions_mode}` | Whether the field has show/hide rules, the rules as JSON, and `show` or `hide` |
| `{field_has_conditions_require}`, `{field_conditions_require}` | The same, for require-if rules |
| `{field_repeats}`, `{repeat_markup}` | Whether this item is a [repeating section](/docs/formidable/building-forms/repeating-sections#in-your-own-markup), and the whole section's markup, with its rows and buttons. The section's other fields are not listed again. |

### `{field_options}`

Inside `{fields}`, loops over a field's resolved choices, whatever their source. It is empty for a field without choices.

| Variable | |
| --- | --- |
| `{value}`, `{label}` | The choice's value and label |
| `{selected}` | Whether it is currently chosen |
| `{option_id}`, `{option_index}` | An id for the choice's input, and its position |
| `{option_attributes}`, `{option_label_attributes}` | The `option` and `option_label` regions |

```ee title="A select"
<select {field_attributes}>
    {field_options}
        <option value="{value}"{if selected} selected{/if}>{label}</option>
    {/field_options}
</select>
```

### Named fields

Every variable in the loop is also available outside it, by handle: drop the leading `field_` and put `field:HANDLE:` in front.

| In the loop | By name |
| --- | --- |
| `{field_label}` | `{field:email_address:label}` |
| `{field_attributes}` | `{field:email_address:attributes}` |
| `{label_attributes}` | `{field:email_address:label_attributes}` |
| `{field_options}…{/field_options}` | `{field:email_address:options}…{/field:email_address:options}` |

A field placed by name is not rendered again inside `{form_meta}`, so an invisible field placed by hand posts once.

## Pages and sections in your own markup

`{form_fields}` renders each page through the theme's `_page` part and each section through `_section`. To write that structure yourself, loop `{form_layout}`: the pages this render shows, which is all of them, or the one `page=` names.

```ee title="templates/default_site/apply.group/index.html"
{exp:formidable:form form_handle="application"}
    <form {form_attributes}>
        {form_meta}
        {form_page_progress}
        {form_layout}
            <div {page_attributes}>
                {if page_name}<{page_heading_tag}>{page_name}</{page_heading_tag}>{/if}
                {page_sections}
                    <fieldset {section_attributes}>
                        {if section_name}<legend>{section_name}</legend>{/if}
                        {section_fields}
                            {field_template}
                        {/section_fields}
                    </fieldset>
                {/page_sections}
                {page_nav}
            </div>
        {/form_layout}
    </form>
{/exp:formidable:form}
```

Keep `{page_attributes}`, `{section_attributes}` and `{page_nav}`: they carry the `data-formidable-page`, `data-formidable-section` and navigation hooks the stepper uses.

| Page variable | |
| --- | --- |
| `{page_number}`, `{page_id}` | Position (from 1) and stable id |
| `{page_name}`, `{page_description}` | From the builder |
| `{page_heading_level}`, `{page_heading_tag}` | `2` and `h2`, unless changed |
| `{page_attributes}`, `{page_heading_attributes}`, `{page_description_attributes}` | Region attributes |
| `{page_content}` | The page's sections, rendered |
| `{page_sections}…{/page_sections}` | One row per section |
| `{page_nav}` | The page's Back, Next and Submit buttons, rendered |
| `{page_is_first}`, `{page_is_last}`, `{page_is_current}` | Where the page sits |
| `{page_state}` | `complete`, `current` or `upcoming` |
| `{page_has_back}`, `{page_has_next}`, `{page_has_save}` | Which buttons the page renders. Save is there only with [save and resume](/docs/formidable/submissions/save-and-resume) on. |
| `{page_previous_label}`, `{page_next_label}`, `{page_save_label}`, `{page_submit_label}` | Their text, defaults filled in |
| `{page_nav_attributes}`, `{page_back_attributes}`, `{page_next_attributes}`, `{page_save_attributes}`, `{page_submit_attributes}` | Region attributes |

| Section variable | |
| --- | --- |
| `{section_id}`, `{section_name}`, `{section_description}` | From the builder |
| `{section_heading_level}`, `{section_heading_tag}` | `3` and `h3`, unless changed |
| `{section_attributes}`, `{section_heading_attributes}`, `{section_description_attributes}` | Region attributes |
| `{section_content}` | Each field's `{field_template}` |
| `{section_fields}…{/section_fields}` | One row per field, with every field variable |
| `{section_repeats}` | Whether it is a [repeating section](/docs/formidable/building-forms/repeating-sections). Its `{section_content}` is then its rows, through the theme's `repeat` part. |

`{form_pages}` has the same rows for **every** page, for a step indicator. Mark each step with `data-formidable-page-step="{page_number}"`, and the script keeps `aria-current="step"` and `data-formidable-page-state` up to date as the visitor moves. See [Multi-page forms](/docs/formidable/building-forms/multi-page-forms#a-custom-step-indicator).

## Errors

After a failed submission:

| Variable | |
| --- | --- |
| `{form_has_errors}` | Whether the last submission failed validation |
| `{form_error_count}` | How many fields failed |
| `{form_errors}…{/form_errors}` | One row per error: `{error_name}` (the field's label), `{error_handle}`, `{error_message}`, `{error_item_attributes}` |
| `{error:HANDLE}` | One field's message, such as `{error:email_address}` |
| `{value:HANDLE}` | One field's submitted value |
| `{error_wrapper_attributes}`, `{error_heading_attributes}`, `{error_list_attributes}` | The summary's regions |

```ee title="An error summary written by hand"
{if form_has_errors}
    <div {error_wrapper_attributes}>
        <p {error_heading_attributes}>Please check {form_error_count} answer(s):</p>
        <ul {error_list_attributes}>
            {form_errors}
                <li {error_item_attributes}>{error_name}: {error_message}</li>
            {/form_errors}
        </ul>
    </div>
{/if}
```

## After a successful submission

A form whose `return=` comes back to its own page shows its success state once, on the next page load.

| Variable | |
| --- | --- |
| `{form_success}` | Whether the previous request succeeded |
| `{form_success_message}` | The message: see `success_message=` |
| `{submission_id}`, `{submission_handle}` | The stored submission, if the form stores submissions |
| `{submission:HANDLE}` | One answer, only with `success_values="yes"` |
| `{success_wrapper_attributes}`, `{success_message_attributes}` | The notice's regions |
| `{form_draft_saved}`, `{form_resume_url}` | Whether the previous request saved a draft instead, and the link back to it. See [Save and resume](/docs/formidable/submissions/save-and-resume). |

## Closed forms

A form past its closing date or submission limit, or a members-only form shown to a guest, renders its message instead of its fields. To place the message inside your own markup, mention `form_closed` in the tag body:

```ee title="templates/default_site/contact.group/index.html"
{exp:formidable:form form_handle="contact_us"}
    {if form_closed}
        <p class="notice">{form_closed_message}</p>
    {/if}
{/exp:formidable:form}
```

| Variable | |
| --- | --- |
| `{form_closed}` | True when the form is closed |
| `{form_closed_reason}` | `date`, `maximum` or `members` |
| `{form_closed_message}` | The message for that reason |

## The `:bag` modifier

Any attribute variable can be narrowed or added to where it is used. `only=` and `except=` take pipe-separated attribute names. Any other parameter is layered on as an attribute, with `class` appending:

```ee title="templates/default_site/contact.group/index.html"
<form {form_attributes:bag except="id|class"}>
<input {field_attributes:bag only="id|name|type|value"}>
<label {label_attributes:bag class="form-label"}>
```

## `{if no_results}`

Rendered when no form matches, or the form has no fields, and `debug=` is off.
